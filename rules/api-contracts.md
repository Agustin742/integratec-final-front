# API and Realtime Contracts

Frontend and backend must agree on observable contracts before either side treats an assumption as integration behavior.

## Ownership and distribution

- Each consumed contract **MUST** have an identifiable backend owner and a frontend integration reference.
- The backend owns the authoritative REST specification: an OpenAPI document generated by NestJS (backend decision D4). The frontend generates its types from it with `openapi-typescript` into `src/api/`, calls the API through `openapi-fetch`, and wraps calls in TanStack Query (FD2); see the [technical justification](../docs/technical-justification.md#architecture-decisions).
- The backend commits the generated `openapi.json` (planned path, for example `apps/api/openapi.json`; set by the backend bootstrap) and its CI fails when it is stale. The frontend runs `pnpm api:sync`, which fetches the committed file from the backend repository (`develop` branch, raw GitHub URL or a local checkout path) and regenerates the types; the generated types in `src/api/` **MUST** be committed so contract changes appear in pull request diffs, and the build **MUST NOT** depend on a running backend (FD7).
- Generated types **MUST NOT** be edited by hand and **MUST NOT** be replaced by manually copied or hand-written types.
- Realtime contracts use the same mechanism: the backend generates Colyseus room state types with `@colyseus/schema` codegen and exports message payload types from `packages/contracts`; `pnpm api:sync` pulls them into `src/realtime/`, committed. Contributors **MUST NOT** assume a published type package or a shared workspace for them (FD7).
- Contract decisions **MUST** identify where the authoritative specification lives and how consumers learn about changes.

## Contract content

- Contracts **MUST** specify operation or event names, authentication requirements, input/output shapes, required and nullable fields, and expected failures.
- Lists **MUST** define ordering and, when needed, filtering and pagination behavior rather than rely on client guesses.
- IDs and date values follow [Data and time](./data-and-time.md).
- Realtime contracts **MUST** distinguish commands, acknowledgements, and notifications, including duplicate or out-of-order handling where relevant.
- Frontend adapters **MUST** handle invalid or unsupported responses without silently treating them as valid domain data.
- Decision FD9 (approved by Agustin on 2026-11-02; see the [technical justification](../docs/technical-justification.md#fd9-contract-mocks)): frontend stories build MSW handlers from the published contract (the backend publishes DTOs and OpenAPI entries, stubs allowed, before or with the implementation), so UI work proceeds before the backend lands. MSW **MUST** be used in development and tests only, never in production builds.
- Mocks **MUST** reflect an identified contract and include relevant failures. A passing mock **MUST NOT** be claimed as proof of backend integration.

## Compatibility and verification

- Producers **MUST** coordinate incompatible changes with consumers before adoption; adding a field **MUST NOT** silently change existing field meanings.
- Verification **MUST** exercise representative success and failure responses through the integration boundary.
- Contract examples **MUST** use synthetic data. Permission and transport obligations remain in [Security](./security.md).
